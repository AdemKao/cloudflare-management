# v0.2 API Management Design

This document defines the proposed architecture for the optional Cloudflare API mode planned for `cloudflare-management` v0.2.

The goal is to let a user create a remotely-managed Cloudflare Tunnel from `cfm` when no Tunnel exists yet, while preserving the current v0.1 Tunnel Token workflow for users who only need to run an existing Tunnel.

Tracking issue: #3

## Design goals

- Keep the current low-privilege Tunnel Token workflow working unchanged.
- Preserve users who already ran `cfm add <profile>` before upgrading.
- Add an optional Account API mode for provisioning Cloudflare resources.
- Support adopting an already-existing Tunnel into API management without creating duplicates.
- Keep different companies and client accounts isolated.
- Use narrowly-scoped API Tokens instead of Global API Keys.
- Keep API Tokens and Tunnel Tokens out of Git and out of process command lines.
- Continue using the official `cloudflared` binary for the actual Tunnel connection.
- Keep Cloudflare as the source of truth for Accounts, Zones, Tunnels, DNS, and remote Tunnel configuration.

## Domain model

v0.1 effectively has one local concept: a Tunnel profile.

v0.2 introduces explicit resource boundaries:

```text
Account
  │
  └── Tunnel
       │
       ├── Route / Published Application
       │
       └── Connector
            └── local cloudflared process
```

### Account

Represents one Cloudflare Account/security boundary, normally one company or client.

An Account may hold:

- Cloudflare Account ID;
- API Token reference;
- optional default Zone metadata;
- one or more Tunnels.

### Tunnel

Represents a remotely-managed Cloudflare Tunnel owned by one Account, or a local token-only record whose Account/Tunnel ID is not yet known to `cfm`.

A Tunnel record may hold:

- local profile/Tunnel alias;
- management mode;
- Tunnel ID when known;
- Tunnel name when known;
- local Tunnel Token reference;
- associated Account alias when known;
- zero or more routes.

Supported management modes should include at least:

```text
token-only   existing/manual Tunnel; local Tunnel Token known, Account/Tunnel ID may be unknown
adopted      existing/manual Tunnel explicitly attached to an Account/Tunnel ID
provisioned  Tunnel created by cfm through Cloudflare API mode
```

### Route

Represents a published hostname mapped to an origin service.

Example:

```text
webhook-dev.example.com
        │
        ▼
http://localhost:3001
```

Route provisioning may require both remote Tunnel configuration and DNS permissions.

### Connector

Represents the local `cloudflared` process started by `cfm` using a Tunnel Token.

The connector lifecycle remains a local concern:

```bash
cfm start <profile>
cfm stop <profile>
cfm restart <profile>
cfm status [profile]
cfm logs <profile>
```

## Two operating modes

### Mode A — Tunnel Token mode

This is the existing v0.1 workflow and must remain supported.

```text
Cloudflare Dashboard
  → create Tunnel
  → obtain Tunnel Token
  → cfm add company-a
  → cfm start company-a
```

This mode does not require an Account-level Cloudflare API Token.

Use it when a developer only needs to run an existing Tunnel.

### Mode B — Account API mode

This mode is optional and intended for users who want `cfm` to create/manage remotely-managed Tunnels.

```text
cfm account add company-a
  → store Account ID + scoped API Token

cfm tunnel create company-a solana-dev
  → create Tunnel using Cloudflare API
  → receive Tunnel ID/token
  → persist local Tunnel metadata/token

cfm start solana-dev
```

A later phase may add automatic route and DNS configuration:

```bash
cfm route add company-a solana-dev \
  --hostname webhook-dev.example.com \
  --url http://localhost:3001
```

## Existing v0.1 users are a first-class upgrade path

A user may already have a working v0.1 setup:

```bash
cfm add company-a
cfm start company-a
```

with local data such as:

```text
~/.config/cloudflare-management/config.json
~/.config/cloudflare-management/secrets/company-a.token
~/.local/state/cloudflare-management/logs/company-a.log
~/.local/state/cloudflare-management/runtime/company-a.json
```

Upgrading to v0.2 MUST NOT require the user to:

- re-run `cfm add company-a`;
- paste the Tunnel Token again;
- provide an Account API Token;
- rename the profile;
- move the existing secret file;
- recreate the Tunnel;
- change the existing start/stop/status/log workflow.

After migration, this must still work immediately:

```bash
cfm start company-a
cfm status company-a
cfm logs company-a
```

### v1 → v2 migration representation

A v1 profile should become a v2 token-only Tunnel record:

```json
{
  "name": "company-a",
  "managementMode": "token-only",
  "account": null,
  "tunnelId": null,
  "tokenFile": "~/.config/cloudflare-management/secrets/company-a.token"
}
```

The absence of `account` or `tunnelId` is valid. It means `cfm` can run the connector but does not yet have enough Account-level metadata to manage the remote Tunnel through the Cloudflare API.

### Account and profile names are separate namespaces

An existing profile alias must not prevent using the same friendly name for an Account alias.

This is valid:

```bash
# Existing v0.1 profile
cfm add company-a

# Optional v0.2 Account registration
cfm account add company-a
```

Internally:

```text
Account alias: company-a
Tunnel/profile alias: company-a
```

The resource type is explicit in the command hierarchy, so a same-name Account and profile are not inherently ambiguous.

## Adopting an existing Tunnel instead of creating a duplicate

After registering an Account API Token, an existing token-only profile may need to become manageable through the API.

The CLI must not assume that `cfm tunnel create` is the correct action. Creating another Tunnel would duplicate a resource that already exists.

Introduce an explicit adoption flow:

```bash
cfm tunnel adopt <account> <existing-profile>
```

Example:

```bash
cfm account add company-a
cfm tunnel adopt company-a company-a
```

The adoption flow should:

1. verify the Account API credential;
2. list/resolve remotely-managed Tunnels in that Account;
3. ask the user to select the matching Tunnel, or accept `--tunnel-id <id>`;
4. persist the Account alias + remote Tunnel ID on the existing local profile;
5. preserve the current Tunnel Token file and token value by default;
6. mark the record as `adopted`;
7. leave the connector's current running/stopped state untouched.

Example:

```json
{
  "name": "company-a",
  "managementMode": "adopted",
  "account": "company-a",
  "tunnelId": "TUNNEL_UUID",
  "tokenFile": "~/.config/cloudflare-management/secrets/company-a.token"
}
```

`cfm tunnel adopt` must never create a new Tunnel.

It also must not silently replace the existing Tunnel Token. Token replacement/rotation should be a separate explicit operation.

## Cloudflare API permissions

Cloudflare's remotely-managed Tunnel API supports creating a Tunnel using:

```text
POST /accounts/{account_id}/cfd_tunnel
```

For Tunnel provisioning, the intended least-privilege account permission is:

```text
Account
└── Cloudflare Tunnel
    └── Edit
```

For automatic public hostname/DNS provisioning, add:

```text
Zone
└── DNS
    └── Edit
```

Tokens should be restricted to the specific Account and, when DNS automation is enabled, only the specific Zone(s) required by that client.

Do not require `All accounts` or `All zones`.

Official references:

- https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel-api/
- https://developers.cloudflare.com/api/resources/zero_trust/subresources/tunnels/subresources/cloudflared/methods/create/
- https://developers.cloudflare.com/fundamentals/api/get-started/create-token/

## Proposed command hierarchy

### Accounts

```bash
cfm account add <name>
cfm account list
cfm account show <name>
cfm account remove <name>
cfm account doctor <name>
```

`cfm account add` should collect:

- local Account alias;
- Cloudflare Account ID;
- API Token through hidden TTY input or `--token-file`;
- optional Zone ID / zone name.

### Tunnels

```bash
cfm tunnel list <account>
cfm tunnel create <account> <name>
cfm tunnel adopt <account> <existing-profile> [--tunnel-id <id>]
cfm tunnel show <account> <name>
cfm tunnel token <account> <name>
cfm tunnel delete <account> <name>
```

`create` and `adopt` are intentionally different operations:

```text
create → remote Tunnel does not exist yet
adopt  → remote Tunnel already exists and the local profile should be attached to it
```

### Routes

```bash
cfm route list <account> <tunnel>
cfm route add <account> <tunnel> --hostname <hostname> --url <origin>
cfm route remove <account> <tunnel> --hostname <hostname>
```

### Convenience workflow

A later phase may add:

```bash
cfm expose company-a \
  --name solana-dev \
  --hostname webhook-dev.example.com \
  --port 3001
```

Possible orchestration:

```text
validate Account API credential
        │
        ▼
select adopted/provisioned Tunnel OR create when explicitly needed
        │
        ▼
store/retain Tunnel metadata + token securely
        │
        ▼
configure hostname → origin
        │
        ▼
create/update DNS when authorized
        │
        ▼
start cloudflared
        │
        ▼
print public URL + diagnostics
```

`cfm expose` must not create a second Tunnel just because a token-only profile already exists. When the intended resource is ambiguous, it should ask instead of guessing.

## Proposed local configuration

Configuration metadata and secrets must stay separate.

Example logical config schema v2:

```json
{
  "version": 2,
  "accounts": {
    "company-a": {
      "accountId": "ACCOUNT_ID",
      "apiTokenFile": "~/.config/cloudflare-management/secrets/accounts/company-a.api-token",
      "defaultZoneId": "ZONE_ID"
    }
  },
  "tunnels": {
    "company-a": {
      "managementMode": "adopted",
      "account": "company-a",
      "tunnelId": "EXISTING_TUNNEL_UUID",
      "tokenFile": "~/.config/cloudflare-management/secrets/company-a.token"
    },
    "solana-dev": {
      "managementMode": "provisioned",
      "account": "company-a",
      "tunnelId": "NEW_TUNNEL_UUID",
      "tokenFile": "~/.config/cloudflare-management/secrets/tunnels/solana-dev.token"
    }
  }
}
```

Suggested local secret layout for newly-created v0.2 credentials:

```text
~/.config/cloudflare-management/
├── config.json
└── secrets/
    ├── accounts/
    │   ├── company-a.api-token
    │   └── company-b.api-token
    └── tunnels/
        ├── solana-dev.token
        └── webhook-dev.token
```

Existing v0.1 token files such as:

```text
~/.config/cloudflare-management/secrets/company-a.token
```

may remain in place. The migration should reference them rather than moving secrets purely for cosmetic consistency.

Secret files should remain mode `0600`; secret directories should remain restrictive.

## Config migration

Existing v0.1 users must not lose profiles.

The implementation should support a deterministic config migration from schema v1 to schema v2.

### Migration requirements

- detect schema v1 automatically;
- create a metadata backup before the first write;
- preserve existing profile names;
- migrate each existing profile as `managementMode: token-only`;
- preserve existing Tunnel Token file paths and values;
- preserve runtime/log path compatibility;
- never require an Account API Token for migration;
- write the new config atomically;
- make migration idempotent;
- leave the previous config recoverable if migration fails;
- never print or copy raw secret values to logs.

### Example migration

Before:

```json
{
  "version": 1,
  "tunnels": {
    "company-a": {
      "tokenFile": "/Users/me/.config/cloudflare-management/secrets/company-a.token"
    }
  }
}
```

After:

```json
{
  "version": 2,
  "accounts": {},
  "tunnels": {
    "company-a": {
      "managementMode": "token-only",
      "account": null,
      "tunnelId": null,
      "tokenFile": "/Users/me/.config/cloudflare-management/secrets/company-a.token"
    }
  }
}
```

The token file itself does not need to move.

## Security boundaries

### API Token and Tunnel Token are different credentials

API Token:

- account/zone scoped;
- may create or modify Cloudflare resources depending on permissions;
- should be treated as the higher-privilege credential.

Tunnel Token:

- tunnel specific;
- used by `cloudflared` to run that Tunnel;
- should remain the preferred credential when no API provisioning is needed.

### Multi-client isolation

Recommended model:

```text
company-a Account
├── Account ID A
├── API Token A
└── Tunnel records owned/adopted by A

company-b Account
├── Account ID B
├── API Token B
└── Tunnel records owned/adopted by B
```

Do not use one unrestricted token across unrelated clients.

### Adoption safety

A token-only profile must not become API-managed automatically.

Adoption requires explicit user action and an explicit remote Tunnel selection/ID.

Do not infer a destructive management relationship from profile naming alone.

### Logging

Never print:

- Account API Token values;
- Tunnel Token values;
- Authorization headers;
- full Cloudflare API request objects if they contain secrets.

Errors should be normalized before being shown to users.

### Destructive operations

Commands such as Tunnel deletion should require explicit confirmation or `--yes`.

Deletion of an adopted Tunnel should make it especially clear that the remote Tunnel existed before `cfm` adopted it.

## API client boundary

The v0.2 implementation should introduce a small Cloudflare API adapter rather than mixing HTTP requests directly into command handlers.

Suggested structure:

```text
src/
├── cli/
├── application/
│   ├── accounts/
│   ├── tunnels/
│   └── routes/
├── cloudflare/
│   ├── client.js
│   ├── tunnels.js
│   ├── routes.js
│   └── dns.js
├── config/
├── secrets/
└── process/
```

Command handlers should orchestrate use cases; HTTP details should remain behind the Cloudflare adapter.

## Failure model

The API/migration layer should distinguish at least:

- invalid or expired API Token;
- insufficient Account permission;
- insufficient Zone permission;
- invalid Account ID;
- invalid Zone ID;
- duplicate Tunnel name;
- ambiguous remote Tunnel during adoption;
- selected Tunnel ID not found in the Account;
- migration backup/write failure;
- Cloudflare 429;
- Cloudflare 5xx;
- request timeout/network failure;
- DNS conflict;
- local secret persistence failure.

No error path should expose raw credentials.

## Implementation phases

### Phase 1 — Account API foundation + safe migration

- config schema v2 + v1 migration;
- metadata backup and atomic writes;
- preserve existing token file paths;
- migrate existing profiles as token-only;
- keep existing connector commands unchanged;
- secure API Token storage;
- Account commands;
- Cloudflare API client abstraction;
- credential/account verification;
- unit tests for migration, idempotency, rollback/recovery, and credential handling.

### Phase 2 — Tunnel provisioning + adoption

- list/create/show/delete Tunnels;
- retrieve/store Tunnel Token for newly provisioned Tunnels;
- `cfm tunnel adopt` for existing v0.1/manual Tunnels;
- interactive adoption selection + `--tunnel-id`;
- preserve existing Tunnel Token during adoption by default;
- never create a duplicate Tunnel during adoption;
- preserve existing connector commands;
- API contract/error tests.

### Phase 3 — Route and DNS provisioning

- remote Tunnel configuration;
- hostname → origin mapping;
- optional DNS management;
- route list/add/remove;
- hostname/origin validation.

### Phase 4 — `cfm expose`

- compose account + tunnel + route + DNS + local connector startup;
- reuse an adopted/provisioned Tunnel when explicitly selected;
- create a Tunnel only when necessary;
- produce a concise final public URL/status summary.

## Non-goals

v0.2 is not intended to:

- replace `cloudflared`;
- implement the Tunnel protocol;
- become a general-purpose Cloudflare administration CLI;
- require Account API mode for existing users;
- auto-adopt an existing Tunnel based only on matching names;
- silently create a duplicate Tunnel when a v0.1 profile already exists;
- store unrestricted cross-client credentials;
- prefer Global API Keys over API Tokens;
- automatically broaden token scopes.

## Acceptance criteria

A v0.2 API-mode implementation is successful when:

1. A user with no existing Tunnel can add a scoped Cloudflare Account credential and create a remotely-managed Tunnel from `cfm`.
2. A user who already ran `cfm add company-a` can upgrade and immediately continue using `cfm start company-a` without re-entering credentials.
3. v1 → v2 migration preserves profile names, token paths, token values, and runtime behavior.
4. Migration is atomic, recoverable, and idempotent.
5. `cfm account add company-a` can coexist with an existing profile alias also named `company-a`.
6. An existing token-only profile can be explicitly adopted into API management without creating a duplicate Tunnel.
7. Adoption preserves the existing Tunnel Token unless replacement is explicitly requested.
8. Newly-created Tunnel Tokens are stored securely and can be used by the existing connector process manager.
9. Route/DNS automation is optional and permission-aware.
10. No API Token or Tunnel Token appears in repository files, logs, or command arguments.
